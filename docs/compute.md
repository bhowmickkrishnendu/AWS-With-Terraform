# Compute design

The compute root creates EC2 infrastructure from a map of instance definitions. It currently manages a running `bastion` instance. The `private_ec2` example in `dev.tfvars` is commented out, so it is not deployed by that file. The root state is `dev/compute/terraform.tfstate`.

## How an instance is built

`main.tf` reads `vpc_id`, `public_subnets`, and `private_subnets` from the networking state in S3. It then uses `for_each = var.instance_definitions` on the EC2 module, SSH key pair, and Secrets Manager resources. The map key becomes part of the Terraform address. For example, the running bastion is tracked under `module.instances["bastion"]`. Renaming `bastion` to another key would change its Terraform address and needs a planned state move or a carefully reviewed replacement.

The EC2 module is pinned to version `6.4.0`. Each entry can override the default AMI, instance type, root volume settings, tags, user data, and extra EBS volumes. `coalesce` chooses an instance value when set and otherwise uses a root default. `subnet_tier` chooses a public or private subnet and `subnet_index` selects its position in the networking output list. The index defaults to zero, so the running bastion stays in its existing first public subnet. A private instance cannot request a public IP through this input. The current bastion entry overrides the defaults with AMI `ami-0ac7b260cf76d8865` and type `t3.small`. Its root volume uses the global 20 GiB `gp3` defaults unless the entry supplies a `root_volume` object.

| Piece | What it does |
| --- | --- |
| `aws_security_group.bastion_sg` | Allows inbound SSH to the bastion and outbound SSH and HTTPS |
| `aws_security_group.private_ec2_sg` | Allows inbound SSH from the bastion security group and outbound HTTPS |
| `aws_iam_role.ec2_ssm_role` | Lets EC2 assume an IAM role |
| `aws_iam_role_policy_attachment.ssm_core` | Attaches `AmazonSSMManagedInstanceCore` |
| `aws_iam_instance_profile.ec2_profile` | Passes that role to instances with `use_iam_profile = true` |
| `tls_private_key`, `aws_key_pair`, Secrets Manager resources | Generate an SSH key, register its public half with EC2, and store its private half in a secret for each instance |

The deployed bastion security group currently permits SSH from `0.0.0.0/0`. Phase 2 code connects its ingress rule to `bastion_ssh_cidr`, and the current value is `10.0.1.0/24`, the first VPC public subnet. The planned update limits SSH to sources in that subnet. It blocks direct SSH from a laptop on the internet, even though the bastion keeps its public IP. The intended administrator path is SSM Session Manager; the bastion was online in SSM during the Phase 2 check. The bastion security group can still send SSH traffic to private instances, and their security group accepts SSH from the bastion security group. The SSH key is generated by Terraform, so its private half is in Terraform state as well as Secrets Manager. The secret uses `recovery_window_in_days = 0`, which gives no recovery window when Terraform deletes it. Review key access, state access, and deletion behavior before extending this design.

From a machine with AWS CLI, the Session Manager plugin, and permission to start sessions, use the current Terraform output to open a shell on the bastion:

```powershell
$env:AWS_PROFILE = 'terraform-dev'
$bastionId = terraform -chdir=environments/dev/compute output -raw bastion_instance_id
aws ssm start-session --target $bastionId --region ap-south-1
```

A future private instance can be reached through the bastion network path with [SSM port forwarding to a remote host](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-sessions-start.html), while its SSH private key stays on the administrator's machine. That private instance is not deployed by the current `dev.tfvars`.

## User data and EBS volumes

`locals.tf` builds the final user data for each instance. It adds a Bash header, an optional script for mounting extra EBS volumes, and the custom script rendered with `templatefile`. The bastion entry points to `scripts/bastion.sh` and passes `hostname = "dev-bastion"`. That script updates packages, installs `htop` and `tmux`, and sets the hostname. It uses `yum`, so its AMI must support that command. A new user data file can use values from its `user_data_vars` map.

`extra_ebs` is typed as a map in `variables.tf` and passes directly to the EC2 module. Use the map form shown in `dev.tfvars` comments. No extra EBS volume is enabled for the current bastion. The Phase 2 mount template waits briefly for a device, checks for an existing filesystem before formatting, writes a filesystem UUID to `/etc/fstab` only once, and mounts only when the target is not already mounted. It still needs the configured Linux device path during the first boot. On EC2 Nitro instances, EBS device names may appear as NVMe names instead, so verify the actual path before enabling an extra volume. AWS [recommends stable EBS identifiers](https://docs.aws.amazon.com/ebs/latest/userguide/identify-nvme-ebs-device.html) because device names can change. Test a new data-volume configuration on a disposable instance before trusting it with data.

The optional subnet index allows spreading future instances across the existing subnet lists, but the current bastion remains at index zero. The private subnets have no NAT gateways, and the current networking values keep NAT disabled. A private instance bootstrap that runs `yum update` needs NAT or another outbound path before it can reach package repositories.

## Inputs, outputs, and checks

`variables.tf` defines the typed instance map and root volume defaults. `dev.tfvars` contains the one active bastion entry. `outputs.tf` exposes the bastion ID and public IP, optional private instance values, key pair names, secret ARNs, and compatibility aliases for older output names. A null private instance output means no `private_ec2` key is active.

```powershell
$env:AWS_PROFILE = 'terraform-dev'
terraform -chdir=environments/dev/compute init -lockfile=readonly -input=false
terraform -chdir=environments/dev/compute validate
terraform -chdir=environments/dev/compute plan -var-file=dev.tfvars -input=false
```

The running bastion ID was matched to its Terraform address during the baseline review. The Phase 2 subnet and EBS refactor alone proposed zero changes. With the current CIDR, the live plan proposes one security-group update and no EC2 replacement. Terraform also reports the existing tag drift notice. Never paste a compute state file or saved plan into an issue or pull request. See [networking.md](networking.md) for subnet routing and [backend.md](backend.md) for state protection.
