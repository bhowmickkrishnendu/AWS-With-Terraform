# Compute design

The compute root creates EC2 infrastructure from a map of instance definitions. It currently manages a running `bastion` instance. The `private_ec2` example in `dev.tfvars` is commented out, so it is not deployed by that file. The root state is `dev/compute/terraform.tfstate`.

## How an instance is built

`main.tf` reads `vpc_id`, `public_subnets`, and `private_subnets` from the networking state in S3. It then uses `for_each = var.instance_definitions` on the EC2 module, SSH key pair, and Secrets Manager resources. The map key becomes part of the Terraform address. For example, the running bastion is tracked under `module.instances["bastion"]`. Renaming `bastion` to another key would change its Terraform address and needs a planned state move or a carefully reviewed replacement.

The EC2 module is pinned to version `6.4.0`. Each entry can override the default AMI, instance type, root volume settings, tags, user data, and extra EBS volumes. `coalesce` chooses an instance value when set and otherwise uses a root default. A `public` instance uses the first public subnet and can request a public IP. A `private` instance uses the first private subnet. The current bastion entry overrides the defaults with AMI `ami-0ac7b260cf76d8865` and type `t3.small`. Its root volume uses the global 20 GiB `gp3` defaults unless the entry supplies a `root_volume` object.

| Piece | What it does |
| --- | --- |
| `aws_security_group.bastion_sg` | Allows inbound SSH to the bastion and outbound SSH and HTTPS |
| `aws_security_group.private_ec2_sg` | Allows inbound SSH from the bastion security group and outbound HTTPS |
| `aws_iam_role.ec2_ssm_role` | Lets EC2 assume an IAM role |
| `aws_iam_role_policy_attachment.ssm_core` | Attaches `AmazonSSMManagedInstanceCore` |
| `aws_iam_instance_profile.ec2_profile` | Passes that role to instances with `use_iam_profile = true` |
| `tls_private_key`, `aws_key_pair`, Secrets Manager resources | Generate an SSH key, register its public half with EC2, and store its private half in a secret for each instance |

The bastion security group currently permits SSH from `0.0.0.0/0`. `bastion_ssh_cidr` is declared and set in `dev.tfvars`, but the rule does not use it. Treat the configured CIDR as ineffective until the code is changed and a plan is reviewed. The SSH key is generated by Terraform, so its private half is in Terraform state as well as Secrets Manager. The secret uses `recovery_window_in_days = 0`, which gives no recovery window when Terraform deletes it. Review key access, state access, and deletion behavior before extending this design.

## User data and EBS volumes

`locals.tf` builds the final user data for each instance. It adds a Bash header, an optional script for mounting extra EBS volumes, and the custom script rendered with `templatefile`. The bastion entry points to `scripts/bastion.sh` and passes `hostname = "dev-bastion"`. That script updates packages, installs `htop` and `tmux`, and sets the hostname. It uses `yum`, so its AMI must support that command. A new user data file can use values from its `user_data_vars` map.

`extra_ebs` is typed as a map in `variables.tf`. The module call contains a fallback path that tries to handle a list, but the declared input type is a map. Use the map form shown in `dev.tfvars` comments. No extra EBS volume is enabled for the current bastion. If you enable automatic mounting, review the generated script first: it calls `mkfs`, uses `|| true`, and appends to `/etc/fstab`. That path has not been made safe for every reboot or an existing data volume. It needs an idempotent filesystem check before production use.

The first public or private subnet is selected by index, so the code does not balance instances across both availability zones. The private subnet has no NAT gateway today. A private instance bootstrap that runs `yum update` may therefore fail unless a suitable network path is added.

## Inputs, outputs, and checks

`variables.tf` defines the typed instance map and root volume defaults. `dev.tfvars` contains the one active bastion entry. `outputs.tf` exposes the bastion ID and public IP, optional private instance values, key pair names, secret ARNs, and compatibility aliases for older output names. A null private instance output means no `private_ec2` key is active.

```powershell
$env:AWS_PROFILE = 'terraform-dev'
terraform -chdir=environments/dev/compute init -lockfile=readonly -input=false
terraform -chdir=environments/dev/compute validate
terraform -chdir=environments/dev/compute plan -var-file=dev.tfvars -input=false
```

The running bastion ID was matched to its Terraform address during the baseline review. The last normal plan proposed zero changes, although Terraform reported a tag drift notice on the bastion. Review that notice before editing its tags. Never paste a compute state file or saved plan into an issue or pull request.
